# Vision Transport

Docker-first ROS 2 Humble vision gateway for moving high-bandwidth perception data over native Zenoh.

The host does not need ROS installed. Build, test, and runtime commands run inside the Docker image defined in `docker/Dockerfile.humble`.

## What It Does

`vision_transport_tx` subscribes to configured local ROS 2 topics only while the remote RX side has a ROS subscriber for the reconstructed output topic. It rate-limits incoming data, keeps only the latest pending sample per stream, encodes it, wraps metadata as CBOR, and publishes the binary envelope over Zenoh.

`vision_transport_rx` subscribes to Zenoh keys, decodes envelopes, reconstructs normal ROS messages, and republishes them locally.

Supported stream types:

- RGB/mono `sensor_msgs/msg/Image`: OpenCV JPEG or PNG.
- Depth `sensor_msgs/msg/Image`: `compressed_depth_image_transport`.
- `sensor_msgs/msg/PointCloud2`: `point_cloud_transport::PointCloudCodec` with `draco`, `cloudini`, `zstd`, or `raw` when the matching plugin is installed.

Set `codec.type: raw` on any stream to disable compression for transmission tests or when a lossy/compressed codec damages downstream data. Zstd is intentionally limited to point-cloud fallback/comparison. It is not used for RGB or depth by default.

For colored point clouds, ROS/RViz commonly uses a field named `rgb` or `rgba` declared as `FLOAT32` even though the bytes contain packed RGB bits. Cloudini applies lossy compression to float fields, so TX protects those packed color fields by encoding them as integer fields for Cloudini and RX restores the original field metadata for RViz.

## Docker Setup

Build the image:

```bash
docker compose -f deployment/compose.yaml build dev
```

Build the ROS workspace:

```bash
docker compose -f deployment/compose.yaml run --rm dev \
  colcon build --symlink-install
```

Run tests:

```bash
docker compose -f deployment/compose.yaml run --rm dev \
  colcon test --event-handlers console_direct+

docker compose -f deployment/compose.yaml run --rm dev \
  colcon test-result --verbose
```

Open a development shell:

```bash
docker compose -f deployment/compose.yaml run --rm dev bash
```

## Running TX and RX

Start TX:

```bash
docker compose -f deployment/compose.yaml up vision_tx
```

Start RX:

```bash
docker compose -f deployment/compose.yaml up vision_rx
```

Both services use host networking and mount `deployment/config/` as `/config`.

## Configuration

TX config: `deployment/config/tx.yaml`

RX config: `deployment/config/rx.yaml`

Each stream is keyed under top-level `streams`. TX needs the source-side fields and codec settings:

```yaml
streams:
  rgb:
    type: image
    input_topic: /camera/color/image_raw
    output_topic: /remote/camera/color/image_raw
    zenoh_key: robot/front_camera/rgb
    max_rate_hz: 10.0
    queue_depth: 1
    resize_scale: 0.5
    codec:
      type: jpeg
      quality: 80
```

RX can be smaller because decode uses the metadata sent by TX:

```yaml
streams:
  rgb:
    type: image
    output_topic: /remote/camera/color/image_raw
    zenoh_key: robot/front_camera/rgb
    queue_depth: 1
```

TX fields:

- `type`: `image`, `depth`, or `pointcloud`.
- `input_topic`: ROS topic TX subscribes to when RX has demand.
- `zenoh_key`: Zenoh data key for encoded envelopes.
- `max_rate_hz`: TX input rate limit. Use `0.0` to disable.
- `queue_depth`: ROS QoS queue depth.
- `resize_scale`: optional resize multiplier for RGB/mono and depth image streams. Depth streams use nearest-neighbor resizing before compressed-depth encoding.
- `voxel_size`: parsed for point-cloud configs; reserved for downsampling policy.
- `codec.type`: image `jpeg`/`png`, depth `compressed_depth`, point cloud `draco`/`cloudini`/`zstd`/`raw`.
- Use `codec.type: raw` to send an image, depth image, or point cloud without compression. Image/depth raw mode still applies configured resize before sending.
- `codec.quality`: JPEG quality, clamped to `1..100`.
- `codec.png_level`: PNG compression level, clamped to `0..9`.
- `codec.zstd_level`: parsed for future Zstd tuning.
- `codec.cloudini_resolution`: parsed for future Cloudini tuning.

RX fields:

- `type`: required so RX knows whether to reconstruct `Image` or `PointCloud2`, and whether an image stream is depth.
- `output_topic`: ROS topic RX republishes.
- `zenoh_key`: Zenoh data key to subscribe to. It must match TX.
- `queue_depth`: optional ROS QoS queue depth. Defaults to `1`.

RX does not need `input_topic`, `max_rate_hz`, resize/downsampling settings, or `codec`. Codec selection is carried in the CBOR metadata envelope generated by TX.

## ROS Parameters

`vision_transport_tx`:

- `config_path`: TX YAML path. Default: `/config/tx.yaml`.
- `zenoh_config_path`: Zenoh config path. Default: `/config/zenoh_tx.json5`.

`vision_transport_rx`:

- `config_path`: RX YAML path. Default: `/config/rx.yaml`.
- `zenoh_config_path`: Zenoh config path. Default: `/config/zenoh_rx.json5`.

Example manual run:

```bash
docker compose -f deployment/compose.yaml run --rm dev bash -lc \
  'source /workspace/install/setup.bash &&
   ros2 run vision_transport vision_transport_tx --ros-args
   -p config_path:=/config/tx.yaml
   -p zenoh_config_path:=/config/zenoh_tx.json5'
```

## Demand-Driven TX Subscriptions

TX does not subscribe to upstream ROS source topics immediately.

For each stream:

1. RX monitors local ROS subscriber count on `output_topic`.
2. RX publishes demand over `zenoh_key + "/_demand"`.
3. TX creates the upstream ROS subscription only while demand is true.
4. TX drops the upstream subscription and clears pending data when demand becomes false.

RX republishes active demand periodically, even when the subscriber count has not changed. This lets a restarted TX learn that demand is already true without requiring the RX-side ROS subscriber to disconnect and reconnect.

This avoids pulling camera/lidar data into the gateway when there is no listener on the RX side.

## Zenoh

Docker configs use explicit TCP peer endpoints instead of multicast discovery:

- `deployment/config/zenoh_tx.json5`: listens on `tcp/0.0.0.0:7447`.
- `deployment/config/zenoh_rx.json5`: connects to `tcp/127.0.0.1:7447`.
- `deployment/config/zenoh.json5`: local no-endpoint fallback.

For two machines, change the RX connect endpoint to the TX host address, for example:

```json5
connect: {
  endpoints: ["tcp/192.168.1.20:7447"],
}
```

Shared memory is disabled in the provided Zenoh configs because the Docker setup is intended to work predictably across container boundaries.

## CycloneDDS Isolation

The provided Compose file sets:

```text
RMW_IMPLEMENTATION=rmw_cyclonedds_cpp
CYCLONEDDS_URI=file:///config/cyclonedds.xml
ROS_DOMAIN_ID=30
```

Edit `deployment/config/cyclonedds.xml` for the robot-local or wired interface that should carry raw DDS. The gateway only saves wireless bandwidth if raw camera/lidar DDS traffic does not also cross the Wi-Fi interface.

Validate isolation with interface counters or packet capture during real deployment.

## Benchmarks

Run the synthetic local codec benchmark:

```bash
docker compose -f deployment/compose.yaml run --rm dev bash -lc \
  'source /workspace/install/setup.bash &&
   ros2 run vision_transport vision_transport_codec_benchmark'
```

The benchmark emits CSV:

```text
case,raw_bytes,payload_bytes,envelope_bytes,payload_to_raw,encode_us,decode_us
```

It covers synthetic RGB raw/JPEG/PNG, depth raw/compressed-depth, raw cloud, Draco, Cloudini, and Zstd. Treat it as a codec baseline, not a Wi-Fi benchmark.

## Runtime Metrics

TX logs per-stream metrics every 5 seconds:

- `published`
- `dropped`
- `errors`
- `last_payload_bytes`
- `last_envelope_bytes`
- `demand_active`

RX logs:

- `received`
- `published`
- `errors`
- `last_envelope_bytes`
- `demand_active`
